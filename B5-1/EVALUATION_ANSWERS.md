## 1. 기능 동작 검증

### [x] String 타입 기본 동작

`SET`, `GET`, `DEL`, `EXISTS`, `DBSIZE`, `KEYS`가 모두 구현되어 있다. 명령어 분기와 인자 개수 검사는 `mini_redis.py:190-247`, 실제 동작은 `mini_redis.py:80-131`에 있다.

- `SET`: 새 키를 저장하거나 기존 값을 덮어쓴다. 성공 시 `OK`를 반환한다.
- `GET`: 존재하는 값을 큰따옴표로 감싸 반환하고, 없는 키는 `(nil)`을 반환한다.
- `DEL`: 삭제 성공 여부를 `(integer) 1` 또는 `(integer) 0`으로 반환한다.
- `EXISTS`: 키 존재 여부를 정수 형식으로 반환한다.
- `DBSIZE`: 현재 유효한 키 개수를 반환한다.
- `KEYS`: 전체 유효 키를 Redis 배열과 유사한 번호 목록으로 반환한다.

각 명령은 먼저 `_purge_expired()`를 호출하므로 만료된 키를 현재 데이터에서 제외한다. 기본 동작과 UTF-8 메모리 계산은 `test_mini_redis.py:85-93`에서 검증한다.

### [x] LRU 자동 제거

`CONFIG SET maxmemory`로 제한을 설정한 후 `SET` 때문에 `used_memory`가 제한을 넘으면 `_evict_if_needed()`가 실행된다. 이 메서드는 LRU 리스트의 꼬리 키부터 삭제하며 제한 이하가 될 때까지 반복한다(`mini_redis.py:72-78`).

LRU 목록은 다음 순서로 관리된다.

```text
head                                               tail
가장 최근 사용(MRU)  <----------------->  가장 오래된 키(LRU)
```

예를 들어 `a`, `b` 순서로 저장한 뒤 `GET a`를 실행하면 `a`가 앞으로 이동하고 `b`가 LRU가 된다. 이후 메모리를 초과하는 `SET`이 실행되면 `b`가 먼저 제거된다. 이 시나리오는 `test_mini_redis.py:95-105`에서 검증한다.

### [x] 메모리 정보 확인

`INFO memory`는 다음 세 항목을 출력한다(`mini_redis.py:138-144`).

```text
used_memory:<현재 사용량>
maxmemory:<메모리 제한>
evicted_keys:<LRU로 제거된 키 누계>
```

`used_memory`는 과제 공식에 따라 다음 값만 계산한다.

```text
Σ(len(key.encode("utf-8")) + len(value.encode("utf-8")))
```

새 키를 저장하면 엔트리 크기를 더하고, 값을 덮어쓰면 이전 크기를 뺀 뒤 새 크기를 더한다. 키를 삭제하거나 만료시키거나 LRU로 제거하면 해당 크기를 뺀다(`mini_redis.py:36-38`, `58-67`, `80-98`). 자료구조 객체, 노드, 버킷의 오버헤드는 포함하지 않는다.

`evicted_keys`는 메모리 제한 때문에 제거된 경우에만 증가한다. `DEL`이나 TTL 만료는 eviction이 아니므로 증가시키지 않는다.

### [x] TTL 관리

`EXPIRE key seconds`는 현재 시각에 초를 더한 `expire_at`을 값 레코드에 기록하고 최소 힙에 `(expire_at, key)`를 삽입한다(`mini_redis.py:146-159`).

- 없는 키에 `EXPIRE`: `(integer) 0`
- 존재하는 키에 정상 TTL 설정: `(integer) 1`
- `seconds <= 0`: 즉시 삭제 후 `(integer) 1`
- 없는 키의 `TTL`: `(integer) -2`
- TTL이 없는 키의 `TTL`: `(integer) -1`
- TTL이 있는 키: 올림한 남은 초 반환

명령 실행 시 `_purge_expired()`가 힙의 루트를 확인한다. 만료 시각이 현재 시각 이하인 항목을 꺼내고, 값 레코드에 저장된 현재 만료 시각과 일치할 때만 키를 삭제한다(`mini_redis.py:45-56`).

TTL을 재설정하거나 `SET`으로 초기화하면 이전 힙 항목은 남을 수 있다. 이 오래된 항목은 현재 레코드의 `expire_at`과 일치하지 않으므로 무시된다. 이것이 lazy deletion 방식이다. TTL 재설정과 만료 동작은 `test_mini_redis.py:126-152`에서 검증한다.

## 2. 구현 구조 설명

### [x] 이중 연결 리스트 구조와 O(1) 연산

`Node`는 `prev`, `next`, `data` 필드를 갖는다(`doubly_linked_list.py:4-10`). 리스트는 전체를 순회하지 않고 양 끝에 바로 접근할 수 있도록 `head`와 `tail`을 보관한다.

- `insert_front`: 새 노드와 기존 `head`의 링크만 변경한다.
- `insert_back`: 새 노드와 기존 `tail`의 링크만 변경한다.
- `remove_front`, `remove_back`: `head` 또는 `tail`을 바로 `remove_node`에 전달한다.
- `remove_node`: 주어진 노드의 앞뒤 노드를 서로 연결한다.
- `move_to_front`: 기존 위치의 앞뒤 링크를 붙인 뒤 해당 노드를 `head` 앞에 연결한다.

각 연산에서 변경하는 노드 수는 데이터 개수와 관계없이 일정하다. 반복문이나 전체 탐색이 없으므로 모두 O(1)이다. 단, `remove_node`가 O(1)이려면 제거할 노드의 참조를 이미 알고 있어야 한다. Mini Redis의 값 레코드가 `lru_node` 참조를 보관하는 이유가 이것이다.

### [x] 직접 설계한 해시 함수

해시 함수는 64비트 FNV-1a 방식을 사용한다(`hash_map.py:25-31`). 입력과 계산 순서는 다음과 같다.

1. 문자열 키를 `key.encode("utf-8")`로 바이트열로 변환한다.
2. 고정 오프셋 값 `14695981039346656037`에서 시작한다.
3. 각 바이트와 현재 해시값을 XOR 한다.
4. 결과에 FNV 소수 `1099511628211`을 곱한다.
5. `& 0xFFFFFFFFFFFFFFFF`로 64비트 범위만 유지한다.
6. 최종 해시값을 버킷 개수로 나눈 나머지를 인덱스로 사용한다.

```text
bucket_index = fnv1a_64(utf8(key)) % bucket_count
```

UTF-8 바이트를 사용하므로 영문뿐 아니라 한글 키도 같은 절차로 처리할 수 있다.

### [x] 체이닝 충돌 해결

버킷 테이블은 인덱스 접근용 배열이고, 각 버킷은 `DoublyLinkedList` 또는 `None`이다(`hash_map.py:19-23`). 서로 다른 키가 같은 버킷 인덱스를 얻으면 해당 버킷의 연결 리스트 뒤에 `HashEntry(key, value)`를 추가한다.

조회 시에는 먼저 해시로 버킷 하나를 선택한 뒤 그 버킷의 연결 리스트만 순회하면서 실제 키를 비교한다(`hash_map.py:36-46`). 삭제 역시 같은 버킷 안에서 키를 찾고 해당 노드를 분리한다. 테스트에서는 모든 키의 해시값을 강제로 0으로 만들어 실제 충돌 상황의 삽입·조회·중간 삭제를 검증한다(`test_mini_redis.py:51-63`).

해시가 고르게 분포하면 버킷당 엔트리 수가 작으므로 평균 O(1)이다. 모든 키가 하나의 버킷에 몰리는 최악의 경우에는 O(N)이 된다.

### [x] 로드 팩터 0.75 초과 시 버킷 확장

로드 팩터는 다음과 같다.

```text
load_factor = entry_count / bucket_count
```

새 키를 삽입한 뒤 로드 팩터가 0.75보다 크면 `_resize(current_capacity * 2)`를 호출한다(`hash_map.py:48-63`). 확장 절차는 다음과 같다.

1. 기존 버킷 배열의 참조를 보관한다.
2. 크기가 두 배인 새 빈 버킷 배열을 만든다.
3. 기존 모든 버킷과 엔트리를 순회한다.
4. 새 버킷 수를 기준으로 각 키의 인덱스를 다시 계산한다.
5. 해당 새 버킷의 연결 리스트에 엔트리를 삽입한다.

버킷 수가 달라지면 `hash % bucket_count` 결과도 달라질 수 있으므로 단순히 배열만 늘려서는 안 되고 모든 엔트리를 재배치해야 한다. 리사이징 한 번은 O(N)이지만 자주 발생하지 않으므로 일반 삽입은 분할 상환 관점에서 평균 O(1)이다.

## 3. 핵심 개념 이해

### [x] LRU에서 해시맵과 이중 연결 리스트의 역할

해시맵은 키로 값 레코드를 평균 O(1)에 찾는다. 값 레코드는 실제 문자열 값뿐 아니라 LRU 리스트 노드의 참조도 가진다(`mini_redis.py:15-21`).

이중 연결 리스트는 사용 순서를 표현한다. 앞쪽은 최근 사용 키, 뒤쪽은 오래 사용하지 않은 키이다. 해시맵만 사용하면 키가 언제 사용됐는지에 따른 순서를 효율적으로 관리하기 어렵고, 리스트만 사용하면 특정 키를 찾기 위해 O(N) 순회가 필요하다. 두 자료구조를 결합해야 조회와 순서 변경을 모두 평균 O(1)에 처리할 수 있다.

### [x] O(1) LRU 달성 원리

성공한 `GET`을 예로 들면 다음 두 단계이다.

1. `HashMap.get(key)`로 값 레코드를 평균 O(1)에 찾는다.
2. 레코드가 보관한 `lru_node`를 `move_to_front()`로 O(1)에 옮긴다.

제거할 키도 리스트의 `tail`에 바로 있으므로 O(1)에 선택할 수 있다. 실제 해시맵 삭제 역시 평균 O(1)이므로 LRU 한 건 제거의 평균 시간 복잡도는 O(1)이다. 해시 충돌이 극단적으로 몰리는 경우 해시 조회와 삭제는 최악 O(N)일 수 있다는 점은 구분해야 한다.

### [x] TTL 관리에 최소 힙을 사용하는 이유

TTL 관리에서 반복되는 핵심 질문은 “다음으로 가장 빨리 만료될 키가 무엇인가?”이다. 모든 키를 매번 순회하면 명령마다 O(N)이 필요하다.

최소 힙은 가장 작은 `expire_at`을 루트에 두므로 다음 만료 항목을 O(1)에 확인할 수 있다. 새 TTL 삽입과 루트 제거는 트리 높이만큼 이동하므로 O(log N)이다. 현재 시각보다 뒤의 루트가 나오면 나머지 항목도 아직 만료되지 않았으므로 정리를 즉시 멈출 수 있다.

### [x] 메모리 초과 시 eviction 흐름

`SET`의 전체 메모리 처리 순서는 다음과 같다(`mini_redis.py:80-99`).

1. 힙을 확인해 이미 만료된 키를 삭제한다.
2. 새 엔트리의 `len(utf8(key)) + len(utf8(value))`를 계산한다.
3. 단일 엔트리 자체가 `maxmemory`보다 크면 저장하지 않고 OOM을 반환한다.
4. 신규 키이면 크기를 `used_memory`에 더한다.
5. 덮어쓰기이면 이전 엔트리 크기를 빼고 새 크기를 더하며 기존 TTL을 초기화한다.
6. 저장한 키를 LRU 리스트의 맨 앞으로 이동한다.
7. `maxmemory > 0`이고 `used_memory > maxmemory`이면 리스트 꼬리의 LRU 키를 삭제한다.
8. 삭제한 키 크기를 `used_memory`에서 빼고 `evicted_keys`를 1 증가시킨다.
9. 제한 이하가 될 때까지 7~8번을 반복한다.

`maxmemory`가 0이면 무제한이므로 eviction을 실행하지 않는다. `CONFIG SET` 자체도 키를 제거하지 않으며 요구사항대로 다음 `SET`에서 초과 여부를 처리한다.

### [x] GET 명령어 전체 흐름

`GET key`의 흐름은 다음과 같다(`mini_redis.py:101-107`).

1. `_purge_expired()`로 현재 시각까지 만료된 힙 항목을 처리한다.
2. 만료가 확정된 키는 데이터 해시맵과 LRU 리스트에서 삭제하고 `used_memory`를 감소시킨다.
3. 해시맵에서 키를 조회한다.
4. 키가 없거나 방금 만료로 삭제되었다면 `(nil)`을 반환한다.
5. 키가 존재할 때만 LRU 노드를 리스트 앞으로 이동한다.
6. 문자열 값을 큰따옴표로 감싸 반환한다.

따라서 만료된 키나 존재하지 않는 키는 LRU가 갱신되지 않는다.

## 4. 확장 사고 및 트러블슈팅

### [x] LRU 대신 LFU를 구현한다면

LFU는 “가장 오래 사용하지 않은 키”가 아니라 “사용 횟수가 가장 적은 키”를 제거한다. 따라서 단일 LRU 리스트만으로는 부족하고 각 키의 접근 빈도를 관리해야 한다.

O(1) 평균 성능을 목표로 한다면 다음 구조로 변경할 수 있다.

- 메인 해시맵의 값 레코드에 `frequency`와 빈도 리스트 노드 참조를 추가한다.
- 빈도별 이중 연결 리스트를 둔다. 예를 들어 빈도 1 목록, 빈도 2 목록처럼 구성한다.
- 빈도 목록을 찾기 위한 별도 커스텀 해시맵을 둔다.
- 현재 가장 작은 빈도를 `min_frequency`로 관리한다.
- `GET` 성공 시 키를 현재 빈도 목록에서 제거하고 `frequency + 1` 목록으로 옮긴다.
- eviction 시 `min_frequency` 목록에서 키를 제거한다.
- 같은 빈도의 키가 여러 개라면 해당 빈도 목록 내부에서는 LRU 순서로 제거해 동률을 해결한다.

더 단순한 대안은 `(frequency, last_access, key)` 최소 힙과 lazy deletion을 사용하는 것이다. 구현은 쉽지만 접근할 때마다 힙 삽입이 필요해 O(log N)이고 오래된 힙 항목이 쌓일 수 있다.

실제 LFU에서는 오래전에 많이 사용된 키가 영원히 남지 않도록 시간에 따라 빈도를 감소시키는 aging 또는 decay 정책도 고려해야 한다.

### [x] 데이터가 10만 건으로 늘어날 때의 병목과 개선

1. **해시맵 리사이징 지연**  
   버킷을 두 배로 늘릴 때 모든 엔트리를 한 번에 재배치하므로 O(N) 지연이 발생한다. 초기 용량을 예상 크기에 맞게 지정하거나, 기존·신규 버킷 테이블을 함께 유지하면서 명령마다 일부 버킷만 옮기는 incremental rehashing으로 지연을 분산할 수 있다.

2. **`KEYS`의 전체 순회와 결과 복제**  
   `KEYS`는 모든 버킷을 순회하고 결과 리스트와 출력 문자열까지 생성하므로 시간과 추가 메모리가 O(N)이다. 대규모 환경에서는 한 번에 일부만 반환하는 커서 기반 `SCAN` 방식이나 iterator 방식이 적합하다.

3. **TTL lazy deletion에 따른 힙 팽창**  
   같은 키에 `EXPIRE`를 반복하면 무효 힙 엔트리가 실제 키 수보다 많이 쌓일 수 있다. 무효 항목 비율이 임계치를 넘으면 유효 TTL만으로 힙을 재구축하거나, 키가 가진 힙 인덱스를 추적해 기존 TTL 항목을 O(log N)에 직접 갱신·삭제할 수 있다.

4. **한 명령에 몰리는 만료 정리**  
   오랫동안 명령이 없다가 요청이 들어오면 `_purge_expired()`가 많은 항목을 한꺼번에 삭제해 지연이 커질 수 있다. 명령당 정리 개수에 예산을 두거나, 실제 서버라면 주기적인 active expiration을 병행할 수 있다.

5. **체이닝과 객체 오버헤드**  
   키 분포가 나쁘면 버킷 연결 리스트 탐색이 길어진다. 더 강한 해시 분산, 버킷 용량 관리, 충돌 체인이 길어질 때 트리로 전환하는 방법을 고려할 수 있다. Python 객체 기반 노드가 많아지는 메모리 오버헤드도 크므로 실제 서비스에서는 더 조밀한 배열 구조나 네이티브 구현이 유리하다.

6. **단일 REPL 처리 구조**  
   현재 과제는 네트워크와 동시성을 제외하므로 문제없지만, 여러 클라이언트가 접속하는 서버로 확장하면 명령 실행, 소켓 I/O, 긴 `KEYS` 작업이 서로를 지연시킬 수 있다. 이벤트 루프, 요청 시간 제한, 점진적 작업 처리가 필요하다.

### [x] 자료구조 오버헤드를 used_memory에 포함한다면

현재 모델은 키와 값의 UTF-8 바이트만 세므로 언어와 실행 환경에 관계없이 결과가 결정적이고 채점하기 쉽다. 실제 메모리를 모델링하면 다음 항목을 추가해야 한다.

- `ValueRecord`, `HashEntry`, 연결 리스트 `Node` 객체 크기
- `prev`, `next`, 키, 값 등의 참조 필드
- 해시맵 버킷 배열의 전체 capacity
- 최소 힙 배열의 capacity와 각 `(expire_at, key)` 엔트리
- 문자열 및 바이트 객체의 헤더와 정렬 패딩
- Python 메모리 할당자의 여유 공간
- lazy deletion으로 힙에 남은 무효 TTL 엔트리

이 경우 같은 논리 데이터라도 Python 버전, 32/64비트 환경, 운영체제, 메모리 할당자에 따라 측정값이 달라진다. `sys.getsizeof()`도 객체가 참조하는 하위 객체를 자동으로 모두 포함하지 않으며, 같은 문자열을 여러 객체가 참조할 때 중복 계산 문제도 생긴다.

공정한 비교와 채점을 위해서는 다음 중 하나를 명시해야 한다.

1. **추상 비용 모델**: 노드, 레코드, 참조, 버킷 슬롯마다 고정 바이트 비용을 정하고 공식으로 계산한다.
2. **통일된 런타임 측정**: 동일한 Python 버전·운영체제·프로세스 조건에서 재귀적 객체 크기 계산 규칙을 사용한다.
3. **프로세스 메모리 차이 측정**: 빈 저장소 기준 RSS와 데이터 저장 후 RSS 차이를 여러 번 측정하고 평균을 사용한다.

과제 채점에는 첫 번째 방식이 가장 재현성이 높다. 이때 버킷의 실제 사용 개수가 아니라 capacity 전체를 포함할지, 공유 객체는 한 번만 셀지, 무효 TTL 엔트리도 포함할지를 반드시 동일한 규칙으로 정해야 한다. 그렇지 않으면 구현 전략의 차이가 데이터 크기보다 점수에 더 큰 영향을 줄 수 있다.
